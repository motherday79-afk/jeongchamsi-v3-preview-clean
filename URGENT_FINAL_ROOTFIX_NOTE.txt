JCV3 URGENT NOW PUBLISH STORAGE FINAL ROOTFIX — 2026-08-30

Observed production error:
- NOW 게시 실패 · STORAGE_REQUEST
- ERR max request size exceeded. Limit: 10485760 bytes, Actual: 10513988 bytes

Root cause addressed in this cumulative patch:
1) Published snapshot family was still able to be bundled into one oversized MSET request on some deployed combinations.
2) The previous CURRENT compactor only replaced news.headlines but spread the rest of each row, so provider/raw baggage could survive compaction.
3) Previous hotfix ZIPs were incremental; applying only a later ZIP could leave an older redis adapter or cleanup path in place.

Fix:
- CURRENT is rebuilt from an explicit allow-list; raw/provider baggage cannot leak through.
- CURRENT keeps bounded fallback news fields only; normal person-public entries still retain the full per-person data path.
- CURRENT/HISTORY/PUBLIC_HOME/PUBLIC_ADMIN/META/category snapshots are written as separate SET requests, never one combined MSET.
- Person-public MSET batches reduced from 40 to 8 entries.
- Redis MSET request budgeting + scanDomains export included cumulatively.
- NOW temp cleanup fallback included cumulatively, so scanDomains export mismatch cannot block publish.
- Storage failures now include the failing domain in the returned detail.

This patch intentionally does not modify AGE/GENDER calculation or JCS scoring logic.
